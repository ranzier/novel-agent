# 亮点一：三层记忆与动态上下文编排

## 2. 背景：为什么长篇小说不能只靠大模型上下文

一次生成一章并不难，连续生成几十万字才是难点。主要矛盾是：

1. 全书正文远大于模型上下文窗口；
2. 即使上下文窗口足够大，全量注入也会带来较高 Token 成本和注意力噪声；
3. 不同历史信息需要不同的保真度；
4. “当前状态”与“历史细节”是两类不同数据，不能只靠向量检索解决；
5. 最近章节的语言和场景连续性不能只用摘要代替。

例如写第 80 章时，模型可能需要同时知道：

- 第 79 章最后谁在现场、谁受伤了；
- 主角现在是什么境界、持有什么物品；
- 第 12 章埋下的某个信物长什么样；
- 哪些伏笔已经回收，哪些仍然开放。

这些信息适合不同的存储与召回方式，因此项目没有把“记忆”简单等同于向量数据库，而是拆成三个层级。

## 3. 总体设计

```text
短期记忆：最近 N 章原文
  目标：高保真保留相邻章节的动作、对白和场景连续性

中期记忆：滚动摘要 + 结构化 WorldState
  目标：低成本保存全局剧情与当前硬状态

长期记忆：历史正文切块 + Embedding + 语义检索
  目标：按当前章节需要，找回早期相关细节
```

三层记忆最终由 `chapter_writer.write_chapter()` 统一组装进 Prompt，而不是分别调用三次生成模型。

## 4. 短期记忆的代码实现

### 4.1 核心入口

文件：`novel_agent/memory/short_term.py`

函数：

```python
recent_context(
    project,
    before_index,
    max_chapters=3,
    char_budget=12000,
)
```

返回值 `RecentContext` 包含：

- `text`：拼接后的近章原文；
- `chapters`：实际纳入的章节编号；
- `truncated`：是否因为字符预算发生截断。

### 4.2 算法过程

1. 从项目中找出当前章之前已经存在的章节；
2. 只取最近 `max_chapters` 章；
3. 从最近一章开始向前填充字符预算；
4. 如果某一章无法完整放入，只保留该章末尾；
5. 最后恢复时间顺序并加上章节分隔标记。

核心逻辑可概括为：

```python
indices = sorted(previous_chapters)[-max_chapters:]

for chapter in reversed(indices):
    remaining = char_budget - used
    if len(body) > remaining:
        body = body[-remaining:]  # 优先保留章节结尾
```

### 4.3 为什么截断时保留尾部

新章节直接承接的是上一章结尾，而不是上一章开头。尾部通常包含：

- 最后一幕所在地点；
- 在场角色；
- 角色即时伤势或情绪；
- 未完成动作；
- 章末悬念。

因此在预算不足时保留尾部，比机械保留前 N 个字符更符合叙事连续性。

### 4.4 短期记忆解决什么，不解决什么

解决：

- 相邻章节场景跳变；
- 对话和语气突然变化；
- 伤势、人物在场状态和未完成动作丢失；
- 重复上一章刚写完的情节。

不解决：

- 很早以前的相关细节；
- 全书当前统一状态；
- 数十章前的伏笔检索。

这正是需要中期和长期记忆的原因。

## 5. 中期记忆的代码实现

### 5.1 数据模型

文件：`novel_agent/memory/state_models.py`

中期记忆由两类数据组成。

#### ChapterSummary

```python
@dataclass
class ChapterSummary:
    index: int
    title: str
    summary: str
    events: list[str]
    characters: list[str]
    foreshadowing: list[str]
    scene_ending: str
```

`scene_ending` 专门记录最后一幕的地点、在场者、即时状态和未完成动作，用于解决摘要过于宏观、无法自然承接下一章的问题。

#### WorldState

```python
@dataclass
class WorldState:
    last_chapter: int
    timeline: str
    protagonist_tier: str
    protagonist_location: str
    characters: list[CharacterState]
    items: list[str]
    open_threads: list[Thread]
    foreshadowing: list[Thread]
```

角色状态包含：

- 姓名；
- 当前境界；
- 生存或受伤状态；
- 当前位置；
- 其他即时备注。

伏笔和进行中的剧情线使用 `Thread` 表示，并记录 `planted_chapter`，便于计算已经悬置多少章。

### 5.2 上下文渲染

文件：`novel_agent/memory/mid_term.py`

函数：

```python
mid_term_block(
    summaries,
    state,
    before_index,
    skip_recent=3,
    max_summaries=30,
    progression_label="",
)
```

渲染顺序：

1. 当前世界状态；
2. 早期章节摘要；
3. 未完成冲突和伏笔；
4. 陈旧伏笔提醒。

最近几章已经以原文形式进入短期记忆，中期记忆会通过 `skip_recent` 跳过这些摘要，避免同一信息重复占用上下文。

### 5.3 硬状态显式化

世界状态会明确输出：

```text
【当前世界状态】（截至第 N 章）
时间：...
主角境界/官职/状态：...
主角位置：...
主角持有：...
在场/相关角色：...
已死亡（不可再出场）：...
进行中的冲突/任务：...
未回收伏笔：...
```

其中死亡角色会单独列出并标记“不可再出场”，这是通过显式约束降低“死人复活”概率，而不是期待模型自己从几十条摘要中推断。

### 5.4 陈旧伏笔提醒

`STALE_AFTER = 8`。当伏笔或任务从埋设到当前章节达到阈值时，上下文会标注：

```text
[已埋 8 章未回收，宜推进/回收]
```

这不是自动决定必须回收，而是给写作模型一个节奏提示，减少伏笔长期悬空。

## 6. 长期记忆的代码实现

### 6.1 章节切块

文件：`novel_agent/memory/retrieval.py`

`split_chapter()` 默认参数：

- 目标块大小约 300 字；
- 硬上限 450 字；
- 优先按空行划分的自然段聚合；
- 去除 Markdown 标题行。

为什么不直接按固定字符切割：固定长度可能把一段对白或动作链从中间切开，降低向量语义质量，也不利于召回后直接注入。

### 6.2 建立索引

`index_chapter()` 的流程：

```text
删除该章旧索引
  -> 按段落切块
  -> 构造 ch{chapter}#{index} 唯一 ID
  -> 批量调用 Embedding
  -> 写入向量矩阵和元数据
```

重写章节时先执行 `remove_chapter()`，避免同一章节的旧正文和新正文同时存在于召回结果中。

### 6.3 Embedding 调用

文件：`novel_agent/memory/embedder.py`

`Embedder` 通过 OpenAI 兼容客户端调用 DashScope Embedding 接口，并按批次处理文本。没有 `DASHSCOPE_API_KEY` 时，写作流程会静默降级，不影响正文生成、状态抽取和审查。

注意简历口径：当前 `config.py` 默认模型是 `text-embedding-v4`。如果简历保留 `text-embedding-v3`，需要能说明实际运行版本或项目升级过程；更稳妥的写法是 `DashScope Embedding`。

### 6.4 NumPy 向量存储

文件：`novel_agent/memory/vector.py`

持久化结构：

```text
vectors.npy       float32 向量矩阵
vectors_meta.json 与矩阵每一行对应的片段元数据
```

向量写入时先进行 L2 归一化：

```math
\hat{x} = \frac{x}{\|x\|_2}
```

查询向量同样归一化后，可以用点积计算余弦相似度：

```math
\cos(\theta) = \hat{q} \cdot \hat{x}
```

检索复杂度大致为 `O(n * d)`：

- `n` 是单本书片段数量；
- `d` 是向量维度。

在单书几千片段规模下，NumPy 矩阵运算足够快，且不需要部署额外向量数据库。

### 6.5 时间边界和去重策略

`recall_block()` 调用 `VectorStore.search()` 时传入：

- `before_chapter`：只允许召回当前章之前的内容，防止未来剧情泄露；
- `exclude_recent`：排除最近章节，避免与短期原文重复；
- `top_k`：控制注入数量；
- `min_score`：过滤低相关片段。

写第 50 章时，如果 `exclude_recent=3`，长期记忆不会召回第 47 至 49 章，因为这些章节已经由短期记忆提供原文。

### 6.6 原子持久化

向量矩阵和元数据都不是直接覆盖：

1. 在目标目录创建临时文件；
2. 写入内容并 `flush`；
3. 调用 `fsync`；
4. 使用 `os.replace` 原子替换目标文件；
5. 异常时清理临时文件。

这可以降低进程中断时生成半文件的风险。但需要准确说明：矩阵和元数据是两个文件，各自原子写，并不是跨文件的数据库事务。

## 7. 三层记忆如何进入正文 Prompt

文件：`novel_agent/generate/chapter_writer.py`

`write_chapter()` 会同时调用：

```python
recent = recent_context(...)
mid_term = mid_term_block(...)
```

长期召回内容则由 `engine.write_one_chapter()` 提前计算，以 `recall_text` 参数传入。

最终 Prompt 结构大致是：

```text
设定圣经
写作风格
本卷弧光
相关角色
世界状态与前情摘要
向量召回的相关历史片段
上一章结尾连续性提示
最近章节原文
本章细纲
下一章剧情边界
作者本章要求
节奏控制
```

这就是项目中的 Context Engineering：不是把所有材料简单拼接，而是明确每类上下文的职责、顺序、预算、去重规则和时间边界。

## 8. 三层记忆的面试表达

### 一句话版本

> 我将长篇记忆拆成最近原文、结构化状态与摘要、历史语义召回三层，并通过预算、时间过滤和去重统一编排上下文，降低长篇生成中的历史遗忘和状态漂移。

### 面试官追问：三层记忆是否能消除幻觉？

建议回答：

> 不能完全消除。它主要降低因上下文缺失造成的遗忘型和编造型幻觉。最终还需要结构化状态合并、一致性审查和提交门禁兜底。

### 面试官追问：为什么不用纯 RAG？

建议回答：

> RAG 擅长找相关历史片段，但不适合直接维护“当前谁已死亡、主角现在什么境界”这类唯一状态。当前硬事实需要结构化 WorldState，相邻细节需要最近原文，所以三层职责不能互相替代。

# 亮点二：双层一致性校验、自动重写与事务式记忆提交

## 9. 背景：有上下文仍然会写错

即使三层记忆提供了足够信息，大模型仍可能出现：

- 正文因为流式中断停在半句；
- 引号没有闭合；
- 已死亡角色重新正常行动；
- 主角境界无原因倒退；
- 角色名称漂移；
- 时间线冲突；
- 金手指能力突破设定；
- 摘要和正文描述不一致；
- 抽取 JSON 可以解析但缺少有效事实。

因此，记忆解决“给模型看什么”，一致性系统解决“模型写完后能否相信”。

## 10. 正文完整性前置检查

文件：`novel_agent/editor/checker.py`

函数：

```python
body_integrity_checks(index, body)
```

它在事实抽取之前运行，检查正文是否为空、引号是否成对、结尾是否疑似被截断等结构问题。

为什么必须前置：

```text
如果残缺正文先进入抽取器
  -> 抽取器可能返回不完整摘要或空状态
  -> 系统可能误以为抽取成功
  -> 错误状态进入后续记忆
```

当前实现的顺序是：

```text
生成 / 风格处理
  -> 正文完整性检查
  -> 事实抽取
  -> 一致性审查
```

## 11. 事实抽取：模型只报变化，程序控制状态

文件：`novel_agent/memory/extractor.py`

核心设计不是让 LLM 输出完整 `WorldState`，而是让它输出：

```json
{
  "facts": [
    {"type": "summary", "text": "..."},
    {"type": "event", "text": "..."},
    {"type": "character", "text": "..."},
    {"type": "foreshadowing", "text": "..."},
    {"type": "scene_ending", "text": "..."}
  ],
  "state_changes": {
    "timeline": null,
    "protagonist_tier": null,
    "protagonist_location": null,
    "character_updates": [],
    "items_add": [],
    "items_remove": [],
    "open_threads_add": [],
    "open_threads_resolve": [],
    "foreshadowing_resolve": []
  }
}
```

### 11.1 为什么不用完整状态覆盖

如果每章要求模型返回完整状态，漏字段会有严重后果：

- 本章没提到某物品，模型返回空列表，历史物品被清空；
- 本章没提到旧伏笔，未回收伏笔丢失；
- 模型错误返回章节号或标题；
- 新旧角色列表互相覆盖。

因此项目定义了所有权边界：

| 数据 | 所有者 |
| --- | --- |
| 本章事实、明确状态变化 | LLM 抽取 |
| 章节号、标题、`last_chapter` | 程序 |
| 未变化字段继承 | 程序 |
| 物品、角色、线索和伏笔合并 | 程序 |
| 最终 schema | Python dataclass |

### 11.2 增量合并

`_merge_world_state()` 先复制上一章状态，再应用显式变化：

```text
新状态 = 上一章状态
       + 新增物品 - 移除物品
       + 角色字段更新
       + 新剧情线 - 已解决剧情线
       + 新伏笔 - 已回收伏笔
```

标量变化为 `null` 时继承旧值；数组为空时表示没有变化，而不是清空整个历史集合。

### 11.3 内容校验与修复

`LLMGateway.complete_json()` 先处理 JSON 语法错误；`extractor._validate_facts()` 再处理“JSON 合法但内容无效”的情况。

二者区别：

- 语法修复：缺括号、代码块包裹、非法 JSON；
- 语义校验：摘要过短、关键事件缺失、结尾场景缺失、结构不符合契约。

内容校验失败时，抽取器将原始任务、校验错误和上次返回一起发给模型修复一次。再次失败则抛出 `MemoryValidationError`。

## 12. 双层一致性校验

文件：`novel_agent/editor/checker.py`

### 12.1 第一层：确定性规则

`rule_checks()` 使用设定圣经、角色库、上一章状态、新状态、摘要和正文进行检查。

适合规则化的问题包括：

- 境界是否沿力量体系序列无故倒退；
- 已死亡角色是否重新出现在出场角色或正文中；
- 是否出现疑似角色名称漂移；
- 状态变化是否违反显式设定；
- 正文结构是否完整。

规则层优势：

- 结果确定；
- 可复现；
- 不增加 LLM 调用成本；
- 可以直接给出具体证据。

局限：规则无法可靠判断复杂人物动机、时间线语义和剧情因果。

### 12.2 第二层：LLM 语义审查

`llm_checks()` 将设定、角色、旧状态、新摘要、新状态和正文交给审查模型，要求返回结构化问题列表。

适合语义判断的问题：

- 人物行为是否违反人设；
- 时间线是否自洽；
- 金手指是否越界；
- 世界规则是否被破坏；
- 事实抽取是否与正文一致；
- 剧情因果是否合理。

### 12.3 统一问题模型

`editor/models.py` 定义：

```python
class Severity(str, Enum):
    ERROR = "error"
    WARN = "warn"

@dataclass
class Issue:
    severity: Severity
    category: str
    message: str
    evidence: str
    source: str
```

`ReviewResult.has_errors` 只由 `ERROR` 决定。警告会展示给用户，但不必阻断记忆提交。

因此简历中“仅当文章没有任何问题才提交”不够准确，正确口径是：

> 事实抽取成功且不存在未解决硬错误时提交；普通警告可以保留并提交。

## 13. 自动重写闭环

文件：`novel_agent/engine.py`

核心循环：

```text
attempt += 1
生成候选稿
  -> 风格处理
  -> 完整性检查
  -> 事实抽取
  -> 一致性审查
  -> 有硬错误且未超过 max_rewrites？
       是：将错误整理成 revision_note，重新生成
       否：退出循环
```

传入重写 Prompt 的信息形如：

```text
- [完整性] 章节疑似在半句处中断
- [角色状态] 已死亡角色再次正常行动
- [力量体系] 主角境界无理由倒退
```

每一稿开始前都会把 `summary`、`new_state` 和 `review` 清空。原因是新稿可能改变事实，不能沿用上一稿的抽取和审查结果。

### 13.1 为什么技术故障不触发正文重写

如果是抽取 API 超时、JSON 连续无效或记忆 payload 校验失败，问题不一定来自正文内容。盲目重写正文只会增加成本，而且无法保证解决接口故障。

当前实现会：

- 保存正文；
- 记录“记忆固化”错误；
- 不更新摘要、世界状态和向量索引；
- 不消耗正文自动重写次数。

这体现了内容错误和基础设施错误的分类处理。

## 14. 事务式记忆提交

### 14.1 提交条件

`engine.write_one_chapter()` 中，记忆提交条件是：

```python
consolidate_mem
and summary is not None
and new_state is not None
and not has_unresolved_errors
```

向量索引还会额外要求：

- Embedder 和 VectorStore 已初始化；
- 没有未解决硬错误；
- 需要固化记忆时，摘要和状态抽取成功。

### 14.2 成功路径

```text
写正文文件
  -> upsert 章节摘要
  -> 更新 WorldState
  -> 用实际摘要回写大纲
  -> 自动晋升反复出场的新角色
  -> 写审查结果
  -> 建立本章向量索引
```

### 14.3 失败路径

```text
写正文文件
  -> 保存审查报告
  -> 不写章节摘要
  -> 不覆盖 WorldState
  -> 不写向量索引
```

为什么仍保存正文：

- 便于作者人工查看和修复；
- 避免模型生成成本完全浪费；
- 审查报告能和具体候选稿对应；
- 后续可以覆盖重写或单独回填记忆。

### 14.4 为什么称为“事务式”，而不是“数据库事务”

这里的“事务式”指应用层提交门禁：只有一组条件全部满足，才更新一组派生记忆。

它不具备数据库事务的全部 ACID 语义。正文、摘要、状态和向量是多个文件，并没有统一的跨文件回滚日志。因此面试时更严谨的说法是：

> 带校验门禁的类事务式记忆提交策略。

### 14.5 历史章节重写保护

`write_one_chapter()` 有 `update_world_state` 参数。重写非最新章节时传 `False`：

- 可以更新该章正文；
- 可以更新该章摘要；
- 不允许旧章节的局部状态覆盖当前最新 `state.json`。

例如已经写到第 30 章，再重写第 5 章，不能把全局状态回退到第 5 章末。

## 15. 一致性亮点的测试证据

相关测试：

- `tests/test_body_integrity.py`
- `tests/test_memory_validation.py`
- `tests/test_engine_style_polish.py`

关键案例：

1. 未闭合引号和半句结尾会被识别；
2. 残缺正文不会进入事实抽取；
3. 模型返回 `index=999` 也不能覆盖程序拥有的当前章节号；
4. 模型遗漏变化字段时，旧物品、旧角色备注和旧伏笔不会被清空；
5. 无效事实修复一次后仍失败，会抛出 `MemoryValidationError`；
6. 记忆抽取失败时不会提交摘要和状态，也不会因为技术错误反复重写正文。

## 16. 一致性系统的面试表达

### 一句话版本

> 我将可确定的问题交给规则引擎、复杂叙事问题交给 LLM 审查，并把硬错误反馈给生成模型重写；只有事实抽取成功且无未解决硬错误时才提交摘要、状态和向量索引。

### 面试官追问：为什么规则检查放在 LLM 前面？

> 结构问题和明确状态冲突可以低成本、确定性地发现，没必要都交给 LLM；同时正文完整性必须在事实抽取前检查，避免残稿生成错误记忆。

### 面试官追问：为什么不直接丢弃错误正文？

> 正文保存和记忆提交是两个边界。正文可以作为候选稿供人工修复，但不能成为后续 Agent 的记忆来源，因此保留正文、阻断派生状态更符合实际创作流程。

# 亮点三：Qwen3-8B + QLoRA 段落级去 AI 腔微调

## 17. 背景：为什么要增加专门的编辑模型

Claude 能生成完整章节，但中文网文仍可能出现：

- “不是 X，而是 Y”式解释；
- 机械转折和段末升华；
- 套路化比喻；
- 对话全部变成短句；
- 过度心理描写；
- 相似动作和程度副词重复；
- 为达到字数而增加静态描述。

直接让大模型重写整章有三个问题：

1. 成本高；
2. 大部分自然段落会被无意义重写；
3. 容易改变数字、专名、对白归属和剧情事实。

因此项目把任务定义为“局部编辑”而不是“二次创作”。

## 18. 任务定义

固定 System Prompt 的核心约束：

```text
只修改语言表达；
不得新增、遗漏或改变剧情事实；
不得改变人物关系、专名、数字、时间、地点、境界和道具；
不得续写、扩写或解释；
原文自然时保持原样；
只输出可以直接替换原文的最终文本。
```

固定 Instruction：

```text
请对以下文本进行最小必要的去AI腔改写；仅在确有必要时修改，原文自然则保持原样。
```

这个任务定义强调三点：

- 最小修改；
- 支持原样保留；
- 事实不变。

## 19. 为什么选择段落级而不是整章级

项目采用“段落优先、句子例外”：

- 一次默认输入完整段落；
- 单句段落自然就是句子级样本；
- 多句动作链和对白不能拆开；
- 超长段落应在完整句群边界切分；
- `---` 等场景分隔符不进入改写模型。

段落级相较整章级的优势：

- 修改范围可控；
- 失败可以局部回滚；
- 保留章节整体结构；
- 并发处理更容易；
- 训练样本构造和人工复核成本更低。

相较单句级的优势：

- 能理解代词指代；
- 保留对白和动作关系；
- 不破坏递进、转折和节奏；
- 避免前后句口吻不一致。

## 20. 为什么选择 Qwen3-8B + 4-bit QLoRA

选择依据来自 `docs/去AI腔局部改写模型微调决策报告.md`：

- Qwen3-8B 具备较好的中文语义和指令理解能力；
- 8B 规模仍能在有限单卡资源下训练和部署；
- QLoRA 将基础模型以 4-bit 量化加载，只训练低秩适配器；
- 相比全参数微调显著降低显存消耗；
- 任务窄、输出短，适合通过参数高效微调学习稳定编辑行为；
- 推理关闭 thinking，避免输出思维链或解释文本。

### QLoRA 的面试解释

LoRA 假设权重更新可以近似为低秩矩阵：

```math
W' = W + \Delta W, \quad \Delta W = BA
```

其中 `A` 和 `B` 的秩远小于原始权重矩阵维度，只训练少量参数。QLoRA 进一步将冻结的基础模型权重量化到 4-bit，减少显存占用，而适配器仍以较高精度训练。

## 21. Alpaca 数据契约

数据字段：

```json
{
  "system": "固定局部编辑器约束",
  "instruction": "固定最小必要改写任务",
  "input": "原始段落",
  "output": "人工确认后的改写，或与 input 完全相同"
}
```

训练和线上推理必须使用一致的消息结构。否则模型训练时学习的是 `system + instruction + input`，线上却只收到裸文本，行为会发生分布偏移。

### 21.1 keep 与 rewrite 样本

数据不能只有“必须改写”的段落，还要包含 `keep` 样本：

- `keep`：输入输出完全相同，训练模型判断“不需要改”；
- `rewrite`：只做必要修改，不改变事实。

如果训练集全部都是 rewrite，模型会形成“无论输入是否自然都必须改”的倾向，导致过度编辑。

### 21.2 数据切分与泄漏控制

相邻段落来自同一章节，随机逐段切分容易造成训练集和测试集高度相似。更合理的方式是按章节或书籍切分，并冻结测试集。

`scripts/build_dataset.py` 实现了：

- 目标样本数校验；
- ID 去重；
- 跨 split 输入去重；
- 固定字段顺序；
- 固定 System / Instruction；
- keep 输入输出一致性；
- rewrite 输入输出差异校验；
- 测试集内容和 SHA-256 冻结；
- manifest 记录数据版本和来源文件哈希。

## 22. 关于“1000 条人工数据”和“90% 通过率”的证据边界

当前仓库数据文档明确标记现有导出为 draft 数据：

- `review_status = review_required`；
- `human_confirmation = false`；
- `training_ready = false`；
- rewrite 输出需要逐条人工确认后才能作为金标准。

当前仓库也没有完整保存 QLoRA checkpoint、训练日志和 90% 指标计算脚本。

因此面试前必须准备仓库之外的真实实验材料，否则不要把以下内容说成代码仓库已经证明：

- 1000 条是否全部人工确认；
- 具体训练超参数；
- 使用的 GPU、训练耗时和 loss；
- 90% 指标定义；
- 与未微调模型的对照结果。

如果确实完成了实验，应准备一张表：

| 指标 | Base Qwen3-8B | QLoRA 模型 | 判定方式 |
| --- | ---: | ---: | --- |
| 风格改写通过率 | 待填 | 待填 | 人工双人复核或明确 rubric |
| 事实保持率 | 待填 | 待填 | 自动规则 + 人工复核 |
| keep 准确率 | 待填 | 待填 | 自然段是否原样保留 |
| 过度改写率 | 待填 | 待填 | 不必要修改占比 |

“改写优化通过率 90%”至少要明确分母、通过标准和评测者，否则是不可解释指标。

## 23. 微调亮点的面试表达

### 一句话版本

> 我把去 AI 腔定义为事实保持约束下的段落级最小编辑任务，构建 keep/rewrite 混合的 Alpaca 数据，并用 4-bit QLoRA 对 Qwen3-8B 做参数高效微调。

### 面试官追问：为什么不是训练一个完整小说模型？

> 完整创作需要世界知识、规划和长上下文，训练成本很高；实际问题只是少量段落存在模板化表达，所以把模型职责收窄成局部编辑器，数据需求和事实漂移风险都更低。

### 面试官追问：为什么训练 keep 样本？

> 线上大部分自然段不应该被修改。没有 keep 样本，模型容易学习成“每次都必须重写”，会提高过度编辑率并增加事实漂移。

# 亮点四：llama.cpp 部署、并发处理与安全回滚

## 24. 本地部署背景

去 AI 腔是每章都会调用的固定后处理，如果持续调用外部大模型，会增加：

- API 成本；
- 网络延迟和不稳定性；
- 小说正文外发风险；
- 并发处理限制。

项目使用 llama.cpp 将量化模型部署成本地 OpenAI 兼容服务，业务代码通过标准客户端访问。

## 25. LocalStyleClient

文件：`novel_agent/editor/style_polisher.py`

职责：

- 从配置读取本地服务 URL、模型名、超时、最大 Token 和温度；
- 使用 OpenAI 兼容 API；
- 启动处理前检查服务是否可用；
- 为每个段落发送固定 System 和 Instruction；
- 清理模型输出中的多余标记；
- 将服务异常转换成可理解错误。

对应配置在 `novel_agent/config.py`：

```text
STYLE_POLISH_ENABLED
STYLE_POLISH_BASE_URL
STYLE_POLISH_MODEL
STYLE_POLISH_TIMEOUT
STYLE_POLISH_CONCURRENCY
STYLE_POLISH_MIN_CHARS
STYLE_POLISH_MAX_CHARS
STYLE_POLISH_MAX_TOKENS
STYLE_POLISH_TEMPERATURE
```

## 26. StylePolisher 段落处理

`StylePolisher.polish_chapter()` 的处理过程：

```text
按空行保留分隔切分章节
  -> 判断段落是否符合处理长度与结构条件
  -> 对 eligible 段落并发调用本地模型
  -> 按原顺序收集输出
  -> 对每段执行 validate_rewrite
  -> 安全则使用改写结果
  -> 不安全或调用失败则使用原段
  -> 拼回完整章节并返回统计
```

并发数由 `STYLE_POLISH_CONCURRENCY` 控制。由于每个段落彼此独立，适合使用线程池并发网络请求；最终按原位置回填，保证章节顺序不变。

## 27. 哪些段落不会送入模型

`_eligible()` 会跳过：

- 太短的文本；
- 超过最大字符数的段落；
- Markdown 标题；
- `---` 等场景分隔符；
- 不适合作为自然语言编辑单元的内容。

这样既减少无意义调用，也避免场景结构被模型破坏。

## 28. 安全回填校验

`validate_rewrite(source, output, protected_terms)` 是本地模型接入中最关键的防线。

### 28.1 数字校验

提取阿拉伯数字和中文数字序列，比较前后是否一致。例如：

```text
原文：三十名戍卒
输出：二十名戍卒
结果：numeric_token_changed
```

### 28.2 数量表达校验

不仅比较数字，还比较数字与量词组合，避免“三十名”变为“三十里”等变化。

### 28.3 专名保护

从设定圣经、角色库和大纲中递归收集人名、地名、功法、势力、物品等候选专名。如果原文中的受保护词在输出中消失，则回滚。

例如：

```text
原文：李恒走进横浦关
输出：他走进关城
```

虽然语句通顺，但丢失了 `李恒` 和 `横浦关`，可能破坏事实精度。

### 28.4 否定关系校验

统计“未、不、无、没有、并非”等否定表达，防止：

```text
原文：他没有答应
输出：他答应了
```

当前是启发式数量检查，不能覆盖所有语义否定，但能阻挡一类高风险改写。

### 28.5 对白结构校验

比较引号数量及引号内数字签名，避免模型破坏对白边界或修改对白中的关键数值。

### 28.6 元文本检查

如果模型输出包含“改写结果：”“分析：”或推理标记，不允许直接回填正文。

### 28.7 为什么校验失败选择回滚而不是再次请求

段落润色不是核心生成任务。失败时继续重试会增加延迟，也可能再次改变事实。原文已经可用，因此最可靠的降级策略是直接保留原段。

## 29. 分级降级策略

项目设计了三层降级：

1. **输出不安全**：只回滚当前段落；
2. **某段请求异常**：只保留该段原文，其他段继续处理；
3. **本地服务整体不可用**：关闭本章后续风格处理，保留完整 Claude 初稿。

风格优化失败不能阻断核心写章流程，因为它是质量增强步骤，不是内容正确性的前置条件。

## 30. 为什么风格处理必须在事实抽取之前

`engine.py` 的顺序是：

```text
Claude 初稿
  -> Qwen 最终正文
  -> 完整性检查
  -> consolidate(Qwen 最终正文)
  -> review(Qwen 最终正文)
  -> 保存 Qwen 最终正文
```

如果先根据 Claude 初稿抽取记忆，再将 Qwen 改写版本保存：

- 保存正文和摘要可能不一致；
- 审查的不是最终用户看到的内容；
- 即使风格模型不应改变事实，也不能假设它永远正确。

测试 `test_polished_text_is_used_for_memory_and_persistence` 明确验证：传给 `consolidate()` 的正文、最终保存正文和返回结果都是 Qwen 处理后的版本。

## 31. 本地部署亮点的面试表达

### 一句话版本

> 我用 llama.cpp 将量化 Qwen 模型部署为 OpenAI 兼容服务，在生成后按段并发处理，并通过数字、数量、专名、否定关系和对白结构校验实现不安全改写的局部回滚。

### 面试官追问：本地模型服务挂了怎么办？

> 风格处理是非核心增强能力，整体不可用时直接保留 Claude 初稿；单段失败只回滚该段，不影响其他段和后续记忆链路。

### 面试官追问：规则校验是否能证明事实完全没变？

> 不能。当前规则重点保护高风险可提取事实，属于工程防线而不是形式化证明。更完整的方案可以增加实体关系抽取、语义蕴含模型和人工抽检。

# 补充亮点：可控生成与工程化

## 32. 确定性节奏引擎

文件：`novel_agent/generate/pacing.py`

系统将章节分为：

- 铺垫；
- 蓄势；
- 爆发；
- 高潮；
- 余韵。

分类依据包括卷内位置、是否卷末、本章是否标记爽点、距离上次爽点的章节数。它不调用 LLM，结果稳定可解释。

设计思想：

> LLM 负责具体情节和语言表达，规则系统负责宏观节奏约束。

## 33. 下一章剧情边界

`chapter_writer._next_boundary_block()` 将下一章细纲作为当前章不能跨越的边界注入 Prompt，避免模型一次性提前写完后续高潮。

这解决的是生成模型常见的“剧情消费过快”问题，而不是传统的一致性问题。

## 34. 统一 LLM Gateway

文件：`novel_agent/llm/gateway.py`

能力包括：

- 普通补全；
- 流式补全；
- JSON 输出解析和修复；
- 瞬时错误指数退避；
- 开始流式输出后不再自动重试，避免重复正文；
- 按任务选择模型；
- Token 和成本统计。

业务代码不直接访问 Anthropic SDK，因此模型调用策略集中、可测试、可替换。

## 35. Reporter、SSE 与单书写锁

`Reporter` 将业务进度和显示方式解耦：

- CLI 使用 `ConsoleReporter`；
- Web 使用 `QueueReporter`；
- `delta` 事件传输正文增量；
- `close()` 哨兵表示整条 SSE 流结束。

`TaskManager` 为每个书籍 slug 维护一把写锁。同一本书不能同时执行两个写任务，因为它们会共享并修改 `state.json`、摘要和向量索引；不同书籍仍可以并行。

批量写作中，每一章都会发送 `done`，但只有整个任务结束才能发送队列结束哨兵。提交记录中曾修复“第一章完成后 SSE 提前关闭”的问题，这能体现对事件语义和任务生命周期的理解。

## 40. 最终复述

> Novel-Agent 的核心不是封装一次大模型调用，而是围绕长篇生成建立一套可控状态机。输入侧用三层记忆和动态上下文编排解决模型看不完整本书的问题；输出侧让 LLM 只抽取事实变化，由程序合并世界状态，再通过规则和 LLM 双层审查发现错误。错误可以反馈重写，但只有通过校验的内容才进入摘要、状态和向量索引，从而阻断错误传播。文风层面，我把去 AI 腔拆成独立的段落级局部编辑任务，用 QLoRA 微调 Qwen3-8B，并通过 llama.cpp 本地部署；线上再用数字、专名、否定关系和对白结构规则做安全回滚。整个设计的关键词是分层记忆、职责边界、失败隔离和可控降级。
