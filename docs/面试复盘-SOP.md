## 0. 先记住这段项目介绍

### 30 秒版本

Novel-Agent 是一个面向十万字级长篇网络小说的智能创作系统。核心问题不是让模型写出一章，而是让模型连续写几十万字后仍然记得人物、设定、时间线和伏笔，并且能够发现错误、自动修正、阻断错误状态继续传播。

我围绕这个问题实现了三层记忆、动态上下文编排、规则与 LLM 双层一致性校验、反馈驱动重写和事务式记忆提交；另外用 QLoRA 微调 Qwen3-8B 做段落级去 AI 腔处理，并通过 llama.cpp 部署为本地服务接入章节生成链路。

### 2 分钟版本

系统以一本书为隔离单元，每本书保存设定圣经、角色库、分层大纲、章节正文、章节摘要、世界状态、审查报告和向量索引。

写一章时，系统先根据大纲计算本章节奏，再用当前章节标题、摘要和目标召回早期相关片段，同时注入最近章节原文、滚动摘要、结构化世界状态、角色档案、本章细纲和下一章边界。Claude 生成初稿后，先经过本地 Qwen 段落级风格处理，再执行正文完整性检查、事实抽取和一致性审查。若存在硬错误，就把错误反馈注入下一轮 Prompt 重写；若事实抽取失败或最终仍有硬错误，只保存正文和审查报告，不更新摘要、世界状态和向量索引，防止错误记忆污染后续章节。

系统同时提供 CLI 和 FastAPI + React Web 界面。长任务在后台线程执行，使用 Reporter 抽象向 CLI 或 SSE 推送进度；同一本书使用 per-slug 写锁，避免并发修改共享 `state.json`。

## 1. 项目需求：先讲清楚为什么要做

### 1.1 业务场景

长篇网文通常包含几十万字正文、数百章剧情、多角色关系、力量体系、时间线、伏笔和物品状态。普通的“一次 Prompt 调一次模型”方式适合短文本，不适合持续创作。

### 1.2 主要痛点与对应功能

| 痛点 | 具体表现 | Novel-Agent 的应对 |
| --- | --- | --- |
| 上下文窗口有限 | 模型无法同时看到全书，写到后期遗忘早期情节 | 短期原文 + 中期结构化记忆 + 长期向量召回 |
| 记忆噪声过大 | 全量塞入会超长，过多无关摘要会干扰写作 | 字符预算、摘要条数、Top-K、相似度阈值和近期章节排除 |
| 世界状态漂移 | 境界倒退、死人复活、角色位置变化、物品凭空消失 | `WorldState` 结构化快照 + 程序增量合并 |
| 模型会编造或违反设定 | 时间线冲突、金手指越界、剧情因果不成立 | 确定性规则检查 + LLM 语义审查 |
| 错误会向后传播 | 错误摘要或状态一旦写入，后面章节继续基于错误生成 | 校验门禁、事务式记忆提交、非最新章重写不覆盖最新状态 |
| 相邻章节不连贯 | 角色瞬移、伤势消失、上一章动作没有承接 | 最近章节原文 + 上一章收尾场景 + 连续性约束 |
| 剧情提前透支 | 当前章提前写下一章高潮，破坏章节钩子 | 分层大纲 + 下一章剧情边界 |
| 长篇节奏不稳定 | 连续铺垫或高潮密集，爽点分布随机 | 确定性节奏引擎：铺垫、蓄势、爆发、高潮、余韵 |
| AI 腔明显 | 套路化转折、过度解释、机械短句和重复心理描写 | Qwen3-8B 段落级局部改写 + 事实安全校验 |
| 长任务不可观察 | 用户不知道生成到哪一步，批量任务容易误判结束 | Reporter 抽象 + 后台任务 + SSE 进度和正文增量 |

### 1.3 需求优先级

面试时可以把需求分为三层：

1. **内容正确性**：能否遵守设定、保持前后状态一致。
2. **长文本可扩展性**：能否在上下文有限时继续写，并召回早期细节。
3. **生产可用性**：能否批量执行、失败恢复、查看进度、编辑和重写。

文风优化属于内容质量增强，不应放在核心记忆与一致性链路之前。项目的核心工程价值首先是“长篇写得下去且状态不被污染”。

## 2. 整体架构与数据边界

### 2.1 模块分层

```text
CLI / React Web
        |
FastAPI API + TaskManager + SSE
        |
engine.write_one_chapter()  # CLI 与 Web 共用的核心编排
        |
生成层       generate/chapter_writer.py / pacing.py
LLM 层       llm/gateway.py / json_utils.py
记忆层       memory/short_term.py / mid_term.py / vector.py / extractor.py
编辑层       editor/checker.py / style_polisher.py
存储层       project.py / storage.py / 每本书独立目录
```

### 2.2 每本书的持久化数据

```text
books/<slug>/
├── bible.json              # 世界观、力量体系、金手指、规则
├── characters.json         # 角色档案
├── outline.json            # 卷级弧光和章节细纲
├── state.json              # 中期世界状态快照
├── summaries/chapters.json # 章节摘要
├── reviews.json            # 每章审查报告
├── vectors.npy             # 向量矩阵
├── vectors_meta.json       # 向量对应的章节、片段和元数据
└── chapters/chXXXX.md      # 正文
```

### 2.3 为什么采用文件型存储

这是单机个人项目，不需要引入数据库运维成本。每本书自包含，便于备份、查看和导出；向量库采用 NumPy 矩阵加 JSON 元数据，几千个片段规模下暴力余弦检索足够简单稳定，也避免 SQLite 向量扩展在 Python 3.14 环境中的兼容性问题。

需要说明取舍：如果规模扩大到多用户、多书和百万级片段，应迁移到专用向量数据库，并将任务状态、锁和持久化元数据迁移到更可靠的共享存储。

## 3. 一章写作 SOP：最重要的主流程

核心入口是 `novel_agent/engine.py` 的 `write_one_chapter()`。CLI 和 Web 都调用它。

### Step 1：加载项目状态

加载当前书的设定圣经、角色库、世界状态和大纲，取得当前章节的标题、摘要、目标、爽点、章末钩子和出场角色。

关键原则：业务编排不直接依赖 CLI 或 Web 输出，而只依赖 `Reporter` 接口。

### Step 2：长期记忆召回

用当前章节的 `title + summary + goal` 作为查询文本，调用 Embedding 服务得到查询向量，然后在当前章节之前的向量片段中检索。

检索约束包括：

- `before_chapter=chapter`，不能召回当前章或未来章节；
- `exclude_recent` 排除最近几章，因为最近正文已经由短期记忆注入；
- `top_k` 限制返回数量；
- `min_score` 过滤低相关结果。

这样做的原因是：短期记忆负责局部连续，向量召回负责早期相关细节，两者避免重复承担同一职责。

### Step 3：确定性节奏计算

`compute_beat()` 不调用 LLM，根据大纲结构确定节拍：

1. 卷末章：高潮；
2. 卷后续第一章：余韵；
3. 本章有爽点或距离上次爽点达到阈值：爆发；
4. 卷内进度超过 60%：蓄势；
5. 其他：铺垫。

每个节拍会生成紧张度和写作指引，再注入正文 Prompt。设计理由是：文字表达可以交给模型，但宏观节奏不应该完全随机。

### Step 4：组装动态上下文

正文 Prompt 主要由以下内容组成：

- 设定圣经：书名、题材、基调、金手指、力量体系和世界规则；
- 本卷信息：卷级弧光、境界目标；
- 相关角色档案；
- 中期记忆：世界状态和历史摘要；
- 长期记忆：语义召回片段；
- 短期记忆：最近 N 章原文和上一章收尾场景；
- 当前章节细纲：剧情、叙事目的、爽点、钩子和出场角色；
- 下一章大纲边界；
- 作者本章思路；
- 当前节拍指令。

上下文参数可配置：最近章节数、最近正文字符预算、摘要条数、召回数量、最低相似度、续写大纲回看窗口和是否注入下一章边界。

### Step 5：调用 Claude 流式生成

通过统一的 `LLMGateway.complete_stream()` 生成章节。网关统一处理：

- 按任务选择模型；
- 流式 Token 输出；
- API 限流、超时、连接错误的指数退避重试；
- Token 用量和成本统计；
- 文本响应提取。

正文增量通过 `Reporter.delta()` 推送，CLI 可以直接显示，Web 则进入 SSE 流。

### Step 6：本地 Qwen 段落级处理

如果开启风格优化，Claude 初稿先经过本地 Qwen 服务，而不是直接拿去抽取记忆。这样后续记忆和审查都基于最终正文。

处理策略：

- 按段落处理，保留原顺序和场景分隔符；
- 只对长度合适的段落调用本地服务；
- 原文自然的段落允许原样保留；
- 单段失败回退该段；
- 本地服务整体不可用时保留整章 Claude 初稿。

### Step 7：正文完整性检查

在调用事实抽取之前，先检查正文是否可能截断或结构不完整，例如：

- 章节末尾疑似停在半句；
- 引号没有闭合；
- 流式生成在结构上不完整。

原因是残缺正文可能让抽取模型返回空对象，若先抽取再检查，会把不完整状态误当成合法记忆提交。

### Step 8：事实抽取与世界状态合并

抽取器要求模型只返回“本章事实”和“相对上一章的变化”，不允许返回完整的新世界状态。

抽取内容包括：

- 本章摘要；
- 关键事件；
- 出场角色；
- 新增伏笔；
- 结尾场景；
- 时间线变化；
- 主角境界和位置变化；
- 角色状态变化；
- 物品增删；
- 剧情线新增和解决；
- 伏笔回收。

程序负责：

- 固定章节号、标题和 `last_chapter`；
- 对空值和数组设置默认行为；
- 未明确变化的字段继承旧状态；
- 对角色、物品、剧情线和伏笔执行增量合并；
- 校验摘要字段是否足够完整；
- JSON 内容不满足要求时带错误反馈重试一次。

核心设计可以用一句话回答：

> LLM 负责事实抽取，程序负责状态演进。

### Step 9：双层一致性审查

第一层是程序规则检查，适合确定性问题，例如：

- 正文截断和引号未闭合；
- 角色死亡后又被判定为正常行动；
- 境界发生异常倒退；
- 角色名称漂移；
- 状态字段和设定不一致。

第二层是 LLM 语义审查，负责判断：

- 时间线和前文是否冲突；
- 人物行为是否违反角色设定；
- 金手指和世界规则是否越界；
- 新摘要、状态变化和正文是否一致；
- 伏笔和剧情因果是否合理。

### Step 10：反馈驱动重写

如果发现正文或设定硬错误，并且仍有重写次数：

1. 提取错误类别、错误信息和证据；
2. 拼成 `revision_note`；
3. 重新调用章节生成 Prompt；
4. 对新稿重新做风格处理、完整性检查、事实抽取和一致性审查。

每一稿都是独立候选稿，不复用上一稿的摘要或新状态，避免旧稿结果污染新稿。

记忆抽取失败属于技术故障，不会因为重写正文而自动解决，因此系统会保留正文、记录“记忆固化”错误并阻止提交。

### Step 11：事务式提交

章节正文会落盘，但摘要、世界状态和向量索引只有在以下条件满足时才提交：

- 正文完整性检查通过；
- 事实抽取成功并通过字段校验；
- 没有未解决的硬错误；
- 需要记忆固化时，摘要和新状态都存在。

失败时：

- 保留正文，方便人工检查；
- 保存审查报告；
- 不写入章节摘要；
- 不覆盖 `state.json`；
- 不建立本章向量索引。

重写非最新章节时还会传 `update_world_state=False`，避免旧章节状态覆盖已经反映后续进度的最新世界快照。

### Step 12：后处理与索引

提交成功后：

- 追加章节摘要；
- 更新世界状态；
- 用摘要回写章节大纲；
- 自动把反复出现且被状态追踪的新角色晋升到角色库；
- 将正文按段切分并写入向量库；
- 返回章节文本、审查结果、字符数和风格处理统计。

## 4. 三层记忆：面试重点

### 4.1 短期记忆：保局部连续

读取最近 N 章原文，并设置总字符预算。它解决的是最近场景的细节连续性：人物即时位置、伤势、动作、对白和上一章结尾。

### 4.2 中期记忆：保全局状态

使用滚动章节摘要和 `WorldState` 快照，不再依赖模型从全文推断：

- 时间线；
- 主角境界和位置；
- 角色生死、境界、位置和备注；
- 物品；
- 未完成剧情线；
- 未回收伏笔。

### 4.3 长期记忆：按需找历史证据

章节按约 300 字目标、450 字硬上限切片。向量存储使用归一化向量的点积近似余弦相似度，元数据保留章节号、片段 ID、正文和类型。

写当前章节时，用本章大纲作为查询，检索早期相关片段。向量库的职责不是保存“唯一真相”，而是提供相关历史证据；结构化状态和规则校验仍然是可靠性保障。

### 4.4 如何解释“解决长上下文幻觉”

更准确的说法是：三层记忆降低上下文窗口受限导致的历史遗忘和事实缺失，从而降低模型凭空补全的概率；它不能单独消除幻觉，仍需要结构化状态、审查和事务式提交共同兜底。

### 4.5 为什么不只使用向量数据库

向量检索擅长找“语义相关片段”，不擅长直接回答当前角色是否死亡、主角当前境界是什么、某伏笔是否已经回收。结构化世界状态擅长保存可验证的全局事实，短期原文擅长保细节，三者职责不同，不能互相替代。

## 5. 一致性、重写和可靠性 SOP

### 5.1 为什么需要规则 + LLM 两层检查

纯规则无法判断复杂叙事因果和人物行为合理性；纯 LLM 又存在随机性和成本高的问题。项目把可程序化的问题交给规则，把时间线、人物动机和世界规则等语义问题交给 LLM。

### 5.2 为什么先完整性检查，再记忆抽取

如果正文已经被截断，抽取模型可能仍生成一个看起来合法的摘要或空状态。先做完整性门禁，可以防止残缺内容进入记忆。

### 5.3 为什么错误不直接重写记忆

错误状态一旦进入 `state.json`、摘要或向量库，就会成为后续章节的上下文来源，造成错误传播。因此系统选择“正文可保留，记忆不提交”，把内容产出和状态提交解耦。

### 5.4 什么情况会触发自动重写

只有正文或设定层面的硬错误值得重写，例如正文截断、角色状态冲突、境界异常和明确的世界规则越界。LLM 接口故障、JSON 抽取失败等基础设施问题，重写正文通常无法解决，因此只阻断记忆提交并保留诊断信息。

### 5.5 重写历史章节的风险

重写第 5 章时，如果直接把第 5 章生成的新状态写回全局 `state.json`，会覆盖已经写到第 30 章的状态。项目因此允许同步章节摘要和正文，但对非最新章节跳过世界状态覆盖。

## 6. 去 AI 腔小模型：需求到部署的 SOP

### 6.1 需求判断

目标不是训练一个新的小说生成模型，而是做一个职责狭窄的局部编辑器：

- 只改语言表达，不改事实；
- 原文自然时保持原样；
- 处理典型 AI 腔，而不是重写整章；
- 能够低成本本地并发运行。

### 6.2 为什么选择 Qwen3-8B + 4-bit QLoRA

- Qwen 中文能力和指令遵循能力适合中文网文编辑；
- 8B 模型规模适合单卡资源约束；
- 4-bit QLoRA 只训练低秩适配器，显存和训练成本低于全参数微调；
- 本地部署可以降低每章后处理的 API 成本和延迟。

### 6.3 数据规范

训练任务采用 LlamaFactory Alpaca 风格字段：

```text
system      固定编辑器约束
instruction 固定去 AI 腔指令
input       原始段落
output      人工确认后的最终段落，或原样保留
```

当前数据工程脚本定义了 1000 条目标样本，并进行去重、字段顺序、keep/rewrite 一致性、测试集冻结和 SHA-256 清单管理。项目文档还明确要求训练、验证和线上推理使用一致的 Prompt 结构。

### 6.4 训练数据的关键取舍

数据不是简单地把所有句子都改一遍，而是同时包含：

- `keep`：本来就自然，输入输出必须一致；
- `rewrite`：存在 AI 腔，需要最小改写；
- 场景边界和对白结构；
- 数字、专名、时间、地点、境界和因果关系保持约束。

段落是默认处理单位，避免把指代、动作和对白机械拆散。场景分隔符需要原样保留，重写后按原顺序拼回章节。

### 6.5 推理安全约束

`StylePolisher` 对每段输出做回填前校验：

- 数字 Token 是否变化；
- 数量表达是否变化；
- 书中专名是否丢失；
- 拉丁字符或模型标识是否异常变化；
- 否定词数量是否变化；
- 引号和对白结构是否变化；
- 是否出现“改写结果”等解释性元文本。

风险段落自动回滚。段落调用异常只影响当前段，本地服务整体不可用则保留整章原稿。这是“模型提升文风、程序守住事实”的组合策略。

### 6.6 llama.cpp 部署和业务接入

本地模型以 llama.cpp OpenAI 兼容接口提供服务，默认关闭 reasoning，设置稳定模型别名。Novel-Agent 通过 OpenAI 兼容客户端调用，使用并发数配置控制段落处理吞吐。

处理顺序必须是：

```text
Claude 初稿
    -> Qwen 段落级风格处理
    -> 安全校验 / 回滚
    -> 正文完整性检查
    -> 事实抽取
    -> 一致性审查
    -> 记忆提交
```

如果把 Qwen 放在记忆抽取之后，最终落盘文本和结构化记忆可能不一致，因此项目把风格处理放在记忆和审查之前。

## 7. Web、任务和工程化实现

### 7.1 CLI 与 Web 复用

`engine.write_one_chapter()` 不直接打印文本，只调用 `Reporter.step/info/warn/error/done/delta`。CLI 使用 `ConsoleReporter`，Web 使用 `QueueReporter`，因此业务流程只有一份。

### 7.2 TaskManager

长任务包括立项、大纲、单章写作、批量续写、重建记忆和向量重建。任务使用后台线程运行，并保存状态、结果、错误和事件队列。

同一本书通过 `per-slug Lock` 保证同一时间只有一个写任务修改共享状态。否则两个批量任务可能同时读到同一个旧状态，再互相覆盖 `state.json`。

### 7.3 SSE 进度流

Web 端订阅 `/api/tasks/{task_id}/events`，服务端将 Reporter 事件编码为 SSE：

- `step`：主要阶段，例如召回、写作、审查、索引；
- `info`：召回数量、摘要和统计；
- `warn/error`：降级或失败原因；
- `delta`：正文增量；
- `done`：单章或整体任务完成信息。

批量写作曾出现“第一章 done 导致前端提前结束”的问题，后续通过区分单章完成事件和整个任务结束哨兵修复。这是一个很适合面试讲的真实工程 Bug：事件语义必须和流生命周期一致。

### 7.4 文件可靠性

向量矩阵和元数据采用临时文件写入、`fsync` 后 `os.replace` 原子替换；JSON 存储也采用原子写，降低进程中断造成半文件的风险。

### 7.5 LLM Gateway

所有 Claude 调用集中在 `LLMGateway`：

- `complete`：普通文本补全；
- `complete_stream`：流式生成；
- `complete_json`：JSON 提取失败后带错误修复一次；
- 按写作、抽取、审查等任务选模型；
- 统计每次调用的输入、输出、调用次数和估算成本。

这样业务代码不直接绑定 Anthropic SDK，后续可以统一加入限流、缓存或替换模型。

## 11. 高频面试问题与建议回答

### Q1：为什么不用把全文直接塞进 Prompt？

因为全文会超过上下文窗口，且大量无关内容会稀释当前章节真正需要的信息。系统把记忆分层：最近原文保局部连续，结构化状态保全局事实，向量检索按需提供早期相关证据，并通过字符预算和 Top-K 控制噪声。

### Q2：三层记忆和普通 RAG 有什么区别？

普通 RAG 主要解决相关文档召回；本项目还维护了明确的世界状态和最近章节原文。三层记忆分别服务于局部连续、全局状态和历史细节，检索结果也受到章节时间边界与近期排除策略约束。

### Q3：为什么不让 LLM 每章直接生成完整 `WorldState`？

因为模型容易漏字段，空数组会把旧状态清掉，还可能擅自改章节号等程序字段。项目让 LLM 只返回事实和相对变化，程序进行增量合并和旧值继承，降低状态覆盖风险。

### Q4：自动重写会不会无限循环？

不会。调用方传入最大重写次数，超过次数就保存正文和审查报告，不再继续重写。对于记忆抽取或 API 技术错误也不会盲目重写，因为重写正文不能解决基础设施问题。

### Q5：如果重写第 10 章，会不会破坏第 20 章的状态？

不会直接覆盖最新世界状态。重写历史章节时设置 `update_world_state=False`，可以更新该章正文和摘要，但跳过旧状态对当前 `state.json` 的覆盖；必要时再由人工或专门回填流程重建后续记忆。

### Q6：规则检查和 LLM 检查如何分工？

规则检查负责确定性、低成本、可复现的问题，例如引号、截断、角色状态和境界变化；LLM 检查负责时间线、行为动机、世界规则和因果关系等语义问题。前者保证底线，后者覆盖复杂语义。

### Q7：为什么去 AI 腔不直接让 Claude 重写整章？

整章重写会带来事实漂移和成本增加，而且多数段落其实不需要改。项目采用段落级局部编辑，只修改必要段落；用数字、数量、专名、否定关系和对白结构校验，不安全就回滚。

### Q8：为什么需要自己微调 Qwen，而不是直接 Prompt？

如果任务只是少量试验，Prompt-only 足够；当它成为每章的固定后处理步骤时，本地小模型可以降低调用成本、延迟和数据外发风险。微调目标不是超过 Claude 的创作能力，而是稳定执行“最小必要改写、原样保留和事实不变”这类窄任务。

### Q9：QLoRA 解决了什么问题？

全参数微调 8B 模型显存和成本较高。QLoRA 用 4-bit 量化基础模型并训练低秩适配器，在有限 GPU 资源下保留较好的指令适配能力，适合这个局部编辑任务。

### Q10：怎么证明去 AI 腔真的有效？

需要预先冻结测试集，并明确指标。至少区分：风格改写是否达到人工标准、原样保留段落是否被错误改写、事实保持是否通过。还应该和未微调 Qwen、Prompt-only 基线比较，不能只看训练 loss。

### Q11：为什么使用 NumPy 做向量库？

单本书几千段的规模下，NumPy 暴力余弦检索足够快，依赖少、可解释、易备份，也避免引入专用数据库和 C 扩展兼容问题。规模扩大后再迁移 Milvus、pgvector 或其他向量数据库。

### Q12：如何保证 Web 和 CLI 行为一致？

两端调用同一个 `engine.write_one_chapter()`，输出通过 Reporter 抽象分发。CLI 使用终端 Reporter，Web 使用队列 Reporter 和 SSE，不在两端复制写作业务逻辑。

### Q13：如何处理 API 限流和任务中断？

LLM Gateway 对瞬时网络、超时、限流和服务端错误进行指数退避重试；文件持久化采用原子替换；长任务通过后台线程和 SSE 可观察。单书写锁避免两个任务同时读写共享状态。

### Q14：这个项目最大的不足是什么？

当前是一套单机个人项目，任务表和锁主要在内存中，向量检索也是单书暴力检索；真实 DashScope、llama.cpp 和长篇批量写作的端到端评测还不够系统，模型效果指标也需要更严格的冻结测试集、人工标注和基线对比。下一步可以做持久化任务队列、专用向量库、事件溯源状态和正式离线评测集。

## 14. 最后复述模板

> 我做这个项目的出发点是解决长篇小说连续生成的可靠性问题。短文本生成的难点是文采，但长篇生成更难的是状态管理：模型会受上下文窗口限制而遗忘前文，也会把错误状态继续传播。我因此设计了三层记忆，最近原文保证局部连续，结构化摘要和世界状态保证全局事实，向量召回补充早期相关情节。生成后不是直接落盘，而是先做正文完整性检查、事实抽取和规则加 LLM 的一致性审查，发现硬错误就反馈重写；如果抽取失败或仍有硬错误，只保留正文和审查报告，不更新摘要、状态和向量索引。后来我又针对 AI 腔问题，用 QLoRA 微调 Qwen3-8B 做段落级局部改写，并用数字、专名、否定关系和对白结构检查保证风格优化不改变剧情事实，最后通过 llama.cpp 接入原有写作流水线。
